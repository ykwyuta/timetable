## A-01〜A-09 スコープと全体構成

### A-01 単一校・単一年度・認証なし
- **仮定**: DBには学校を1件だけ持ち、認証・ユーザー管理・年度管理を実装しない。
- **根拠**: `docs/requirements.md` 2.5節でスコープ外と宣言済み。E2Eを含めた完成までを
  優先するため、横断的関心事は後回しにした。
- **見直し条件**: 教育委員会単位で複数校を扱う要望が出た時点。School テーブルは
  最初から複数行を持てる形にしてあるため、API のルーティングに `school_id` を
  通す改修で足りる。

### A-02 「講座（Course）」を割当の単位とする
- **仮定**: 時間割のセルに入るのは学級×教科ではなく **Course（講座）** とし、
  Course は「担当教員1名・受講学級1つ以上・週コマ数・使用教室種別」を持つ。
  小中は「1学級＝1講座」に縮退する。
- **根拠**: 要件書 1.4節。高校の選択科目の同時展開と、特別支援学級の交流及び
  共同学習を、同一の仕組みで表現できる。
- **見直し条件**: 生徒個人単位の履修登録を扱う場合、Course と生徒の関連が必要になる。

### A-03 週時間割のみを対象とし、年間時数の管理はしない
- **仮定**: 「週あたり何コマ」までを扱い、年間の授業時数の消化状況や行事による
  振替は扱わない。
- **根拠**: 要件書 2.5節。年間管理まで含めると学校暦・行事予定のモデルが必要になる。
- **見直し条件**: 実運用で「今年度の時数が足りているか」を見たいという要望が出た時点。

### A-04 バックエンド Python / フロントエンド React + TypeScript
- **仮定**: FastAPI + SQLAlchemy + SQLite + PuLP、フロントは Vite + React + TypeScript
  + @dnd-kit。状態管理ライブラリは使わず React の useState/useReducer で足りる規模に留める。
- **根拠**: ソルバー資産が Python にあること、フロントのスタックは利用者が指定済み。
- **見直し条件**: 画面が増えて prop drilling が辛くなった時点で Zustand 等を検討。

### A-05 DBは単一ファイルのSQLite、マイグレーションはAlembicを使わない
- **仮定**: 起動時に `create_all()` でスキーマを作る。Alembicは導入しない。
- **根拠**: まだ運用データが存在せず、スキーマ変更は作り直しで足りる段階のため。
  導入コストをE2E完成に回した。
- **見直し条件**: 実データを投入して運用を始める時点で必須になる。

### A-06 求解ジョブはインプロセスのスレッドで実行する
- **仮定**: Celery/RQ 等は使わず、`ThreadPoolExecutor` で求解し、ジョブ状態は
  プロセス内の辞書に持つ。クライアントは2秒間隔でポーリングする。
- **根拠**: 要件書 2.1節の実測で、必要なのは「25秒かかることがある処理を
  HTTPリクエストの外に出すこと」だけであり、分散ワーカーは過剰。
  CBC の求解は subprocess で走るため GIL の影響を受けない。
- **見直し条件**: 複数プロセスでAPIを動かす（uvicorn --workers 2以上）場合、
  ジョブ状態が共有されないため、DBかRedisに移す必要がある。

### A-07 求解には時間制限を設け、時間内の最良解を返す
- **仮定**: 時間内に最適解が出なければ、その時点の暫定解（実行可能解）を返し、
  最適性が証明できたかどうかを `timed_out` で伝える。
- **根拠**: 要件書 2.1節の実測で最大24.35秒。「解が出ない」で終わらせないため。
- **補足**: 当初は60秒としたが、実装後の実測を踏まえて30秒に変更した（**A-27 参照**）。
- **見直し条件**: 36学級かつ制約を全部有効にした状態で未充足コマが残るなら、
  時間制限の延長か、変数固定によるウォームスタートを検討する。

### A-08 1コマの長さは校種既定（小45分・中高50分）で固定し、UIから変更させない
- **仮定**: 表示上の情報としてのみ持ち、求解には使わない。
- **根拠**: 求解は「コマ枠」の割当問題であり、1コマが何分かは制約に影響しない。
- **見直し条件**: 65分授業や短縮授業を扱う場合。

### A-09 曜日は月〜金の5日固定、1日のコマ数は学校単位の単一値
- **仮定**: 土曜授業は扱わず、曜日ごとに異なるコマ数（月曜だけ5時間等）も持たない。
  1日のコマ数は学校ごとに1つの値（小中6、高6）とし、`periods_per_day` で保持する。
- **根拠**: 週5日制が原則。曜日別コマ数を入れるとUIとソルバーの両方が複雑になるため、
  まず均一なケースを完成させた。週コマ数が枠数を下回る分は空きコマになる。
- **見直し条件**: 高校の7時間目設定や、月曜6時間・金曜5時間といった週時程を
  扱う場合。`periods_per_day` を曜日別の配列に変えれば対応できる設計にしてある。

## A-10〜A-19 ドメインモデルと生成データ

### A-10 特別教室は「種別ごとの同時使用数」で扱う
- **仮定**: 個々の教室（理科室1・理科室2）を講座に割り当てるのではなく、
  「同一コマに理科室を使えるのは2講座まで」という形で制約する。
- **根拠**: 具体的にどの教室かは運用で決まることが多く、求解に第4の次元を
  持ち込むと変数が数倍になる。制約の本質は同時使用数の上限。
- **見直し条件**: 教室ごとに設備差がある（生物室と化学室を区別したい）場合。

### A-11 矛盾する固定は求解前に拒否する
- **仮定**: 固定（ロック）された割当同士がハード制約に違反していたら、求解せず
  違反理由付きでジョブを失敗させる。勝手に固定を外して解くことはしない。
- **根拠**: 固定は利用者の明示的な意思なので、黙って無視するのは裏切りになる。
- **見直し条件**: 「矛盾する固定を自動で最小限だけ外して解く」機能が欲しくなった場合。

### A-12 同時展開群の講座は週コマ数を揃える
- **仮定**: 1つの群に属する講座は同じ週コマ数を持つ前提で生成する。
- **根拠**: 選択科目は同じ時間帯に並ぶため、コマ数が違うと定義できない。
- **見直し条件**: 週2単位と週3単位の科目を同じ選択群に入れたい場合（実在するが稀）。

### A-13 ハード制約は「空解で充足可能」な形にしてモデルの実行可能性を保証する
- **仮定**: H1〜H6 はすべて「1つも配置しない解」で満たせる形にしてある。
  したがってモデルは常に実行可能で、`Infeasible` は返らない。不足は必ず
  S1（週コマ数の未充足）として数値で返る。
- **根拠**: 要件書 1.2節のとおり週30枠に29〜30コマを詰める問題であり、
  「解が返らない」画面を利用者に見せてはいけない。
- **見直し条件**: なし（この設計は要件の中核）。

### A-14 週コマ数は年間標準授業時数から最大剰余法で導出する
- **仮定**: 「年間時数 ÷ 授業週数」の小数部が大きい教科から順に1コマずつ配り、
  合計が総授業時数と一致するようにする。
- **根拠**: 単純な四捨五入では合計が合わない（例: 小3は個別に丸めると28にならない）。
  導出結果は小1=25、小4〜6=29、中=29、高=30となり、施行規則の総授業時数と一致する。
- **見直し条件**: 学校独自の時数配当を使う場合は、この導出を使わず直接入力させる。

### A-15 1つの講座は高々1つの同時展開群にしか属さない
- **根拠**: 複数の群に属すると、どの群の時間帯に従うべきかが定義できない。
- **見直し条件**: なし（多重所属は意味的に破綻するため）。

### A-16 教員1人あたりの担当学級数
- **仮定**: 小学校の専科は外国語4・理科4・算数6・体育6学級、中学校は国語4・社会5・
  数学4・理科4・音楽8・美術8・保健体育6・技術家庭8・外国語4学級、高校は既定4学級。
  ただし A-26 の上限で頭打ちにする。
- **根拠**: 週の持ちコマ数が18コマ前後に収まるように置いた値。実配置は学校ごとに
  異なるため、あくまで初期データの目安。
- **見直し条件**: 実際の校務分掌を取り込む場合は画面から編集する。

### A-17 学級担任を専任の教員として生成する
- **仮定**: 中学・高校でも「1年1組 担任」という教員を作り、道徳・総合・特別活動を
  担当させる。実際の担任は教科も持つが、生成データ上は分けている。
- **根拠**: 担任と教科担任の兼務を自動で割り振ると、特定の教員に偏った不自然な
  データになる。生成物は編集の出発点という位置づけ。
- **見直し条件**: 実際の教員名簿を取り込む機能を作る時点で不要になる。

### A-18 特別教室の既定保有数
- **仮定**: 校種ごとに最低保有数を持つ（例: 中学校は理科室2・音楽室1・美術室1・
  技術室1・体育館1）。実際の数は A-25 の需要計算で増える。
- **見直し条件**: 学校ごとの実際の保有数を入力させる場合。

### A-19 学級担任の持ちコマ上限は週29コマ
- **仮定**: 小学校の学級担任と特別支援学級の担任は週29コマ、教科担任・専科は週18コマ。
- **根拠**: 小学校の担任は1日の大半を自学級で教えるため、教科担任の平均18.1コマ
  （令和4年度教員勤務実態調査）を当てはめると必ず上限超過になる。
- **見直し条件**: 学級担任の負担上限を運用ルールとして持つ場合。

## A-20〜A-28 実装中に判明して置き直した仮定

これらは実装・実測の結果として必要になった変更であり、当初の設計から変えた点。

### A-20 学校生成は「校種 × 1学年あたりの学級数」だけで行う
- **仮定**: 画面からは校種と学級数だけを指定し、教科・教員・講座・教室は自動生成する。
- **根拠**: マスタを手入力させると最初の一歩が重すぎて、自動提案まで到達できない。
- **見直し条件**: CSV取込を実装したら、生成とインポートを選べるようにする。

### A-21 再提案は新しいバージョンとして保存する
- **仮定**: 求解のたびに新しい Timetable を作り、元の版を parent_id で指す。
  上書きはしない。
- **根拠**: 「提案 → 手で直す → 再提案」を繰り返すため、前の版に戻れる必要がある。
- **見直し条件**: 版が増えすぎたら、古い版の自動削除が要る。

### A-22 求解のキャンセルは「結果を保存しない」で実現する
- **仮定**: CBC の求解プロセス自体は中断できないため、キャンセルされたジョブは
  完了後に結果を破棄する。
- **根拠**: 求解は最長でも設定した時間制限で終わるため、実害が小さい。
- **見直し条件**: 時間制限を長く（数分）取る運用にする場合は、CBCをsubprocessとして
  自前で起動して kill できるようにする必要がある。

### A-23 CORS は既定で全許可
- **仮定**: `TIMETABLE_CORS_ORIGINS` が未設定なら全オリジンを許可する。
- **根拠**: 開発とE2Eの利便性。認証がなく秘匿データも持たない段階のため。
- **見直し条件**: 公開運用する前に必ず絞る。

### A-24 同時展開（S4）はLP上は等式（ハード）として扱う
- **仮定**: ソルバーの中では「群の講座は必ず同一コマ」に固定する。検証エンジンは
  引き続きソフト違反として報告する。
- **根拠**: H1（学級の重複）は、選択科目群を「学級から見て1コマ」として数えるために
  群インジケータ z を使っている。S4 を緩めると z と実際の配置が乖離し、
  **H1 が実質的にソフト制約になってしまう**（実際に中学校の生成データで
  「1年1組の火2限に国語と音楽が重複」というハード違反が発生した）。
  空解で充足できるため、モデルが常に実行可能である性質は保たれる。
- **効果**: 手編集で群を崩すことは引き続き可能で、そのときは S4 違反として警告される。
- **見直し条件**: なし（H1の正しさが依存しているため）。

### A-25 特別教室の数は需要から自動算出する（稼働率75%目標）
- **仮定**: 保有数 = max(既定値, ceil(その教室を使う週コマ数の合計 ÷ (週の枠数 × 0.75)))。
- **根拠**: 固定値だと大規模校で物理的に配置不能になる。19学級の小学校では理科だけで
  週36コマ必要なのに、週の枠は30コマしかなく、理科室1室では原理的に解けない
  （実際に未充足34コマの解しか出なかった）。稼働率を100%と仮定すると、その教室が
  全コマ埋まっていないと成立しなくなり他の制約と両立しないため、75%を目標にした。
- **見直し条件**: 実際の保有数を入力させる場合はこの計算を使わない。

### A-26 教員1人あたりの担当学級数は持ちコマ上限で頭打ちにする
- **仮定**: `担当学級数 = min(設定値, 18 ÷ その教科の週コマ数)`。
- **根拠**: 算数専科を6学級担当にすると週30コマとなり、上限18コマを必ず超える。
  その状態ではソルバーがどう解いても S3 違反が残る解しか作れなかった。
- **見直し条件**: 実際の校務分掌を入力する場合は不要。

### A-27 求解は相対ギャップ2%・時間制限30秒で打ち切る
- **仮定**: CBC に `gapRel=0.02`、既定 `timeLimit=30秒` を渡す。
- **根拠**: 実測したところ、解の品質は15秒で頭打ちになり、そこから先の時間は
  すべて最適性の証明に使われていた（15秒でも60秒でも違反件数が同一）。
  最終的な求解時間は小学校19学級で5.3秒、中学校13学級で4.2秒、高校15学級で19.8秒、
  いずれも未充足0コマ・ハード違反0。
- **見直し条件**: 未充足コマが常に残るようなら時間制限を延ばす。

### A-28 交流及び共同学習は「同じ講座に特別支援学級を追加する」形で表現する
- **仮定**: 特別支援学級の体育・音楽・図画工作などは、別講座を作って同時展開群で
  揃えるのではなく、通常学級の講座の受講学級に特別支援学級を加える。
- **根拠**: 当初は同時展開群で実装したが、それだと同じ授業なのに音楽室を2室分
  消費してしまい、音楽室1室の中学校で配置不能になった。実態としても
  「特別支援学級の児童生徒が通常学級の授業に参加する」のだから、講座は1つが正しい。
- **効果**: 教室も教員も二重に数えなくなり、H1・H3 が自動的に正しくなる。
  要件書の S5 は、同時展開制約ではなくデータ構造で保証される形になった。
- **見直し条件**: 特別支援学級が独自の指導内容で同時刻に別室で学ぶ形（交流ではなく
  並行実施）を扱う場合は、同時展開群での表現に戻す。

### A-29 同一講座を同じコマに二重配置する操作はAPIで拒否する
- **仮定**: 移動・追加の際、同じ講座がすでにそのコマにあれば 409 を返す。
- **根拠**: 固定された割当の集合は `(講座, 曜日, コマ)` の集合として持っているため、
  完全な重複を表現できず、矛盾検査をすり抜けてしまう。入口で防ぐのが確実。
- **見直し条件**: なし。

## A-30〜A-34 フロントエンドとE2E

### A-30 求解ジョブのポーリング間隔は1秒
- **仮定**: 要件書では2秒としていたが、実装では1秒にした。
- **根拠**: 小・中規模校は数秒で解けるため、2秒間隔だと体感が鈍い。ポーリングの
  コストは1リクエスト/秒で無視できる。E2Eの所要時間も短くなる。
- **見直し条件**: 同時利用者が増えてAPIの負荷が問題になる場合。

### A-31 E2Eのときだけスキーマを作り直す
- **仮定**: 環境変数 `TIMETABLE_E2E_RESET=1` のときだけ、起動時に
  `drop_all` → `create_all` を実行する。通常起動では既存データを保持する。
- **根拠**: E2Eは毎回まっさらな状態から始めたい一方、開発中の手動確認では
  データが消えると困る。
- **見直し条件**: なし。

### A-32 undo/redo はサーバ側の一括置換で実現する
- **仮定**: フロントが操作前の割当スナップショットをスタックに積み、
  戻すときは `PUT /api/timetables/{id}/assignments` で丸ごと置き換える。
  差分を持たず、履歴もサーバに保存しない（リロードすると消える）。
- **根拠**: 1つの時間割は数百コマ程度で、丸ごと置き換えても実用上問題ない。
  操作ごとの逆操作を定義するより、間違いが起きにくい。
- **見直し条件**: 複数人が同じ時間割を同時に編集する場合は、丸ごと置換だと
  他人の変更を消してしまうため、差分＋競合検出が必要になる。

### A-33 読み込み中はセットアップ画面を出さない
- **仮定**: 学校を選んでから時間割が届くまでの間は「読み込み中」を表示し、
  「学校を作る」画面を出さない。
- **根拠**: E2Eで実際に問題が起きた。学校選択の直後は一瞬 `timetable === null`
  になるため、セットアップ画面が現れ、そこへ入力している最中に時間割が届いて
  画面が入れ替わり、入力が失われた。利用者の操作でも同じことが起こりうる。
- **見直し条件**: なし（実害のあるちらつきの修正）。

### A-34 E2Eはこの環境に用意されたChromiumを直接指す
- **仮定**: `/opt/pw-browsers/chromium` が存在すればそれを `executablePath` に使う。
  存在しなければ Playwright の既定の解決に任せる。
- **根拠**: `@playwright/test` のバージョンによって期待するブラウザのリビジョンが
  変わり、この実行環境に焼き込まれているリビジョンと一致しないことがある。
- **見直し条件**: CI では `npx playwright install chromium` を実行しているため、
  この分岐は使われない。

### A-35 E2Eのビューポートを縦1400pxにする
- **仮定**: Playwright のビューポートを 1440×1400 にし、時間割グリッドと未配置トレイが
  スクロールなしで同時に画面へ収まるようにする。
- **根拠**: ドラッグの途中でスクロールが挟まると座標がずれ、掴み損ねる。実際に
  「コマをトレイへ外す」テストが、トレイを表示するためのスクロールでドラッグ元の
  位置がずれて失敗した。ヘルパー側でも、必要なスクロールを済ませてから両方の
  位置を読むように直したうえで、画面外を掴もうとしたら明示的に失敗させている。
- **見直し条件**: 実利用者の画面ではスクロールが起きるため、ドラッグ中の自動
  スクロール（dnd-kit の AutoScroll）の挙動は別途確認が必要。
